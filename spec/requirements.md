# 神山高専紹介サイト 要件定義

## 1. 目的

神山まるごと高専の紹介ページを、Astro + Tailwind CSS による 1 ページ構成で新規構築し、GitHub Pages の project site として公開できる状態を定義する。初回は仮文言・仮画像でも成立する構成を優先し、後から文章や画像素材を差し替えやすいことを必須条件とする。

## 2. 対象ユーザー

- 入学候補者とその保護者
- 学校の雰囲気を短時間で把握したい一般閲覧者
- 素材差し替えや文言更新を行う運用担当者

## 3. スコープ

- 対象: トップページ 1 ページ、GitHub Pages 公開設定、差し替え可能なコンテンツ構造
- 非対象: CMS 導入、問い合わせフォーム、複数ページ展開、独自ドメイン設定

## 4. 制約と前提

- Astro を使用すること
- スタイリングは Tailwind CSS を優先すること
- Node.js 22 環境でビルドできること
- GitHub Pages は project site として公開すること
- 文章素材と画像素材は存在する前提だが、初回実装時点で置き場所は未確定であること
- 公式サイトへの導線を必ず設けること

## 5. 要件一覧（EARS）

### 5.1 体験要件

- RQ-01: WHEN 利用者がトップページへ初回訪問したとき THE SYSTEM SHALL 学校名とページの主目的が即座に分かるヒーロー領域を表示する。
- RQ-02: WHEN 利用者がトップページを閲覧するとき THE SYSTEM SHALL 学校の特徴を整理した紹介セクションを 1 画面内で順に把握できる構成で表示する。
- RQ-03: WHEN 利用者が学生生活を知りたいとき THE SYSTEM SHALL 学び方や日常の様子を伝える学生生活セクションを表示する。
- RQ-04: WHEN 利用者が詳細情報を求めるとき THE SYSTEM SHALL 公式サイトへ遷移できる明確なリンク導線を少なくとも 1 つ以上表示する。
- RQ-05: WHILE 画面幅がモバイル相当であるとき THE SYSTEM SHALL ヒーロー、カード、導線ボタンの視認性と操作性を維持する。
- RQ-06: WHILE 画面幅がデスクトップ相当であるとき THE SYSTEM SHALL セクション間の階層と情報のまとまりが分かる余白とレイアウトを維持する。

### 5.2 コンテンツ運用要件

- RQ-07: WHEN 初回実装時点で本素材が未投入であるとき THE SYSTEM SHALL 仮文言とプレースホルダー画像で破綻なく成立するページを提供する。
- RQ-08: WHEN 運用担当者が文章や画像を差し替えるとき THE SYSTEM SHALL セクション単位で内容を更新しやすいデータ構造またはファイル配置を提供する。
- RQ-09: IF 一部の画像素材が未提供である THEN THE SYSTEM SHALL 代替テキストとプレースホルダー表現によりレイアウト崩れを防止する。

### 5.3 公開・技術要件

- RQ-10: WHEN 本プロジェクトをビルドするとき THE SYSTEM SHALL Node.js 22 環境で npm run build が成功し、静的出力を生成する。
- RQ-11: WHEN GitHub Pages 用に公開するとき THE SYSTEM SHALL project site の base path を考慮したアセット参照と内部導線を生成する。
- RQ-12: WHEN GitHub Actions でデプロイするとき THE SYSTEM SHALL Astro のビルド成果物を Pages artifact として公開できる workflow を前提に構成される。
- RQ-13: IF base path 設定に不整合がある THEN THE SYSTEM SHALL 検証工程で CSS、画像、内部リンクの崩れを検出できるようにする。

### 5.4 デザイン要件

- RQ-14: WHEN 利用者がページ全体を閲覧するとき THE SYSTEM SHALL 「やわらかいポップ」の印象を与えつつ、学校紹介としての信頼感を損なわない視覚表現を提供する。
- RQ-15: WHERE 再利用可能な紹介ブロックを用いる場合 THE SYSTEM SHALL ヒーロー、特徴、学生生活、外部リンク導線をコンポーネントまたは同等の単位で分離できる設計を採用する。

## 6. 依存関係と制約整理

| 区分 | 内容 | リスク | 緩和策 |
| --- | --- | --- | --- |
| ランタイム | Node.js 22 | ローカルと CI の差異 | workflow でも Node.js 22 を明示する |
| フレームワーク | Astro | project site 用 base 未設定で 404 | astro.config で site/base を固定する |
| スタイリング | Tailwind CSS | デザイン定義が散らばる | トークンをテーマ拡張または CSS 変数へ集約する |
| 配信基盤 | GitHub Pages + GitHub Actions | branch 公開前提で設計すると不整合 | Actions デプロイを正式手段とする |
| コンテンツ | 文章・画像素材 | 素材未確定で実装停止 | 仮素材で進め、差し替え箇所を明示する |
| 外部導線 | 公式サイト URL | URL 未確定で誤リンク | 設計では差し替え可能な定数化を前提にする |

## 7. データフロー要約

1. コンテンツ定義ファイルまたはページ内データから、各セクションへ見出し・本文・画像情報を供給する。
2. Astro が静的 HTML を生成し、Tailwind CSS によるスタイルを適用する。
3. ビルド成果物を GitHub Actions が Pages artifact としてアップロードする。
4. GitHub Pages が project site の URL 配下で配信する。

## 8. エッジケースと失敗条件

| ケース | 想定される問題 | 要求される振る舞い |
| --- | --- | --- |
| 素材未投入 | 空白や崩れが発生する | 仮文言・プレースホルダーで補完する |
| 画像のみ未投入 | カード高さが不揃いになる | 固定比率枠または背景で視覚的整合を保つ |
| base path 誤設定 | CSS や画像が 404 になる | build 後確認で検知し修正できる状態にする |
| 外部リンク未確定 | 誤遷移または未設定になる | 差し替え用定数を明示し検証項目に含める |
| モバイル幅 | ボタンや文字が詰まる | レスポンシブ調整で可読性を維持する |

## 9. 受け入れ基準

- トップページ 1 ページで学校の特徴、学生生活、公式サイト導線が確認できる。
- 仮素材のままでも情報設計とレイアウトが成立する。
- GitHub Pages project site 前提の設定方針が設計に含まれている。
- 将来の素材差し替え箇所が運用担当者にとって追跡可能である。

## 10. 信頼度評価

- Confidence Score: 90%
- 根拠: 目的、ページ構成、公開方式、技術スタックが明確であり、未確定要素は主に素材配置と公式サイト URL のみで、どちらも差し替え前提の設計で吸収可能であるため。
